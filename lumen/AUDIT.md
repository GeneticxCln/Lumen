# Lumen audit

Current state of correctness, security boundaries and release readiness. The earlier version of this file described the Python sidecar and browser bridge, which no longer exist.

## Architecture in one paragraph

Tauri v2 shell (`src-tauri`) over a UI-agnostic Rust core (`crates/lumen-core`: M3U parsing, SQLite, search, TMDB, extraction, harvesting, probing, sync, network guard). Video plays in a separate native mpv window controlled over JSON IPC. The React UI talks only to Tauri commands. There is no browser mode and no local HTTP server. Extraction runs a pinned, checksum-verified `yt-dlp` binary as a subprocess.

## Security boundaries (verified by tests unless noted)

- **Network guard.** User-directed fetches (playlist import, harvest, search providers, extractor update, probes) go through `netguard`: public addresses only unless "allow local network sources" is on, every redirect hop and every resolved address is checked.
- **Network privacy** (Settings → Account → "Network privacy"). An optional local HTTP relay (`crates/lumen-core/src/privacy`) that Rust-side network calls, mpv's own playback traffic, yt-dlp's own extraction requests, and remote images (TMDB art, a playlist's `tvg-logo`) can all be routed through, forwarding to a SOCKS5 or HTTP proxy the user configures. Off by default, and adds no overhead while off: images and metadata keep loading directly, exactly as before this feature existed, until it is turned on. Fail-closed throughout once it is on: a guarded call errors rather than ever falling back to a direct connection if the relay is not running or not yet decided (`Route::Pending` at startup, before settings are read); starting mpv, running yt-dlp, and fetching a remote image all refuse the same way, through `child_proxy_url()`, rather than ever doing any of them unproxied. The relay decides per destination whether to go direct (a local-network source, bypassing the upstream like a VPN split-tunnel) or to the upstream, never resolving a non-local hostname itself so it is not told to the upstream unresolved. mpv is started with `--http-proxy`, `--ytdl=no` and `--load-unsafe-playlists=no` (last, so a user's own `extra_mpv_args` cannot override them) so it cannot reach the network another way — via its own yt-dlp hook or an embedded playlist reference; yt-dlp itself gets `--proxy`, inserted before the `--` that separates its options from the page URL. Both mpv's and yt-dlp's child environments have proxy-related variables (`http_proxy`, `no_proxy`, ...) stripped so an ambient system proxy cannot override what Lumen explicitly set (or left unset). The embedded webview (WebKitGTK) is pointed at the same route as defense in depth — its own requests (favicon prefetch, speculative preconnects) fail closed the same way, via `WebKitWebsiteDataManager::set_network_proxy_settings` — though the frontend no longer needs to rely on that: TMDB art and `tvg-logo` images are now fetched through a Tauri command (`fetch_remote_image`, using the same guarded client as everything else) and handed to the page as a data URL once privacy is on, instead of letting WebKitGTK fetch them itself. Covered by 22 relay tests, 6 `remote_image` tests (fake-server tests for size cap, content-type check, and failure modes) and unit tests for the mpv/yt-dlp argument-building, environment-stripping and webview-proxy-mode logic, plus proving hostnames reach the upstream unresolved, credentials never cross, a local-network target bypasses the upstream, and an unreachable upstream never falls back to a direct connection. The in-window (embedded libmpv) path picks up the same mpv arguments, since it shares the same startup code; its own child environment is this process's own and is not separately scrubbed.
- **Profile PINs.** Enforced in the backend (`authorize_profile`) with a process-wide attempt limiter. A PIN protects against other people using the app, not against reading the database file.
- **Settings.** Only an allowlist of keys is writable from the UI; internal state (active profile, sync cursors) is not.
- **Secrets.** TMDB and search-provider tokens and the sync key live in the OS keychain, never in the settings table. Error text from HTTP failures has the request URL removed.
- **yt-dlp.** The managed binary must match the SHA-256 pinned in `crates/lumen-core/yt-dlp-manifest.json` and the release's published `SHA2-256SUMS`. A test ties the manifest to the upstream checksums, and an ignored live test downloads, verifies, installs and runs it. The pin moves only by editing the manifest in a commit.
- **Sync.** End-to-end encrypted; the server holds opaque blobs (see the README's "Sync" for exactly what it can see). Tested against an in-process server and, with `SYNC_TEST_URL`, against the real Worker.
- **Subtitle lookup.** Off until the user agrees; searches only on request. Every request goes through `netguard` to hosts the service owns (checked again after redirects), answers and downloads are size-capped, and a download must decode to subtitle text before the player sees it. Covered by in-process server tests (oversize, redirect off-host and to a private address, forged download address) and an ignored live test against the real services.
- **ffmpeg.** Local files only, with a timeout, a concurrency limit and a bounded, stable-named thumbnail cache.
- **mpv.** IPC socket in `$XDG_RUNTIME_DIR` (or a private directory), bounded pending requests.

## Identity and extraction

- Library entries are keyed by stable URLs and `content_key`s (`titles`, `title_sources`); favorites and history store a `content_key` and are matched on it as well as on the URL.
- An extracted page is saved as the **page** URL. Its stream link (which expires and may carry tokens) is resolved when the entry plays and is never stored, so replays work and split audio is never lost.
- When a stream fails, playback moves to the next ranked source of the same title and shows a notice.

## Known limitations and open work

- **Release packaging is not proven.** The `.deb` and AppImage build in CI's release workflow definition and were inspected locally, but no release has been published, and no package (`.deb`, AppImage, Flatpak, Arch) has been installed on a clean machine. The Flatpak and Arch package are built from the checkout by `.github/workflows/packaging.yml`; check that workflow's latest run for whether they build.
- **Native playback is not verified on every desktop.** Rust tests pass, mpv IPC and MPRIS are exercised against a real mpv and a real D-Bus session, and the whole path (launch, page, mpv, MPRIS) was run in the real app under a virtual X display, but playback on real GNOME, KDE and Hyprland sessions has not been checked.
- **Single-window playback is an experiment.** On X11/XWayland it was checked by screenshot under Xvfb: one window, video above the controls, setting off gives the separate mpv window. On native Wayland the video renders through libmpv into a GTK GL area; in the real app under a headless Weston (software OpenGL) the frame had video content (about 57% of the pixels lit, the centre matching the test pattern). Not verified: real GNOME, KDE or Hyprland sessions, hardware decoding on this path (the Wayland display is not passed to libmpv, so it may fall back to software decoding), and fullscreen on a real window manager. Controls are beside the video rather than over it. A headless Weston that has run many windows can stop delivering frame callbacks; restart it before testing.
- **Casting is tested against a fake device only.** Discovery, the control calls and serving a file (ranges, one allowed peer, media files only) are tested against an in-process UPnP renderer; no real TV, receiver or speaker has been tried, and TVs differ in what formats, ranges and metadata they accept. Subtitles are not sent, and the device's own volume is not controlled. Chromecast and AirPlay are not supported.
- **Self-update has not replaced a real AppImage.** The release lookup, version comparison, checksum, size and redirect limits and the file swap are tested against an in-process server and temporary files, but no release has been published yet and no AppImage has been updated by a running Lumen, so the restart handoff (a new copy started after the old one exits) is untested. Integrity is a checksum from the same release, not a signature. An AppImage in a folder the user cannot write to cannot update itself and falls back to telling the user.
- **mpv start failures and choppy scrolling (0.1.1).** A released AppImage's environment (library and tool paths into the AppImage) used to be inherited by the host `mpv`; children now get it without those entries (checked in the real app with a simulated `APPDIR`, not in a real AppImage on another distribution). mpv start errors now carry mpv's own last lines and a dead mpv is reported at once. Scrolling changes (no blur on the sticky header, async image decoding, cheaper hover effects, off-screen shelves skipped, smooth scrolling and hardware acceleration requested from WebKitGTK) were checked for rendering only; smoothness itself was not measured and needs a real display. The in-window libmpv path still loads the host's libmpv with the AppImage's own library path in this process.
- **mpv dying mid-session (0.1.3).** A command sent after mpv has already exited used to surface as a bare "Failed to write to mpv socket". It now carries mpv's own last lines, the same way a failed start does ("mpv stopped responding (its control connection closed): ..."). Checked with a fake control socket that answers the startup calls and then closes (not a real mpv crash).
- **Adding many links is checked against an in-process server and a mocked page, not at scale.** Link finding, the playlist check (valid list, HLS, 404, an HTML page, a redirect to a private address, the local-network switch), sampling and cancelling are unit-tested; the dialog was driven in a browser with a mocked backend, and the real app (built, run under Xvfb) was driven through both the paste box and the real native file picker, confirming a chosen file is read from disk and tested the same way as pasted text. Not tried: hundreds of real IPTV links (speed, hosts that block repeated requests), and links that need special headers or a login. Only five sample channels per playlist are tried, so "4 of 5 respond" is a hint, not a guarantee.
- **A light audit pass (0.1.4).** A parallel read-through of `lumen-core`, `src-tauri` and the frontend (not a diff review of one change) found and fixed: a TV episode whose title carries no `SxxExx` marker no longer collapses its favorite/history/resume state onto every other such episode of the same show (`content_key.rs`); starting mpv no longer holds the playback lock for its full startup, so Stop/Pause/Seek sent while a stream is loading no longer wait behind it (`commands.rs`); the in-window (embedded) engine's `is_alive()` no longer always answers `true`, so a crashed embedded player is replaced instead of reused forever (`mpv_ipc.rs`, checked with a fake control socket that closes mid-session); the mpv control socket directory is now checked for private ownership even when inherited from `$XDG_RUNTIME_DIR`, not only on the directory this app creates itself; a launch target (a file, playlist or link opened from outside the window) arriving in the narrow window around the page's first `take_launch_targets` call could previously be queued after that one drain and never delivered — fixed and covered by a concurrency stress test (`launch.rs`); a sync scheduled while another sync was still running could start a redundant parallel cycle instead of being absorbed by the one in flight (`sync.rs`); the search result cache ignored most of the library when keying its cache, so an edit to a channel in the middle of an unchanged-length library could serve a stale result (`search.rs`); a playlist, or a file picked for "Many links", in a non-UTF-8 encoding (Latin-1, Windows-1251, UTF-16, ...) is now decoded instead of turning into a wall of replacement characters (new `text_encoding` module, reused by playlist import and the bulk-link file reader); and three "Many links" dialog bugs — pasting a list that is entirely already-added sources showed "no links found" instead of saying so, the "not tested yet" count could go negative after adding links, and only the first of several add failures was shown while the rest kept their old "success" status. A cast session's progress poll could also stop firing: the interval was torn down and restarted on every unrelated re-render of the window, not just when the cast itself changed (`CastBar.tsx`).
 Synced records still carry the (credential-stripped) stream URL beside the `content_key`; the server cannot read either. Query parameters whose names contain `key`, `auth`, `token`, `secret` or `pass` are removed from synced URLs, which can break a stream whose identity lives in such a parameter on the other device.
- **A second light audit pass.** Another parallel read-through of `lumen-core`, `src-tauri` and the frontend found and fixed: deleting a playlist that carried a favorited channel's only stream re-derived a different sync key for the tombstone than the one the favorite was originally created and synced under, so the removal never reached other devices in the sync group — it now reuses the favorite's own stored `content_key` (`db.rs`, covered by a test asserting the sync queue's item_key is unchanged across the delete); the category-override lookup added for manual corrections built one `IN (...)` query per `list_channels` call with no chunking, which could exceed SQLite's bind-parameter limit on a large aggregated IPTV playlist and fail the whole library view — it now chunks and dedupes the same way `insert_channel_rows` already does, covered by a 150-key test; starting mpv releases the playback lock for its full startup, so a Stop clicked before it finishes, or a second Play racing the first, used to be silently ignored or leave an orphaned, uncontrollable mpv process — a per-attempt ticket now lets a late Stop or a newer Play cancel an in-flight start instead of storing it (`commands.rs`, covered by a test of the ticket/cancellation logic); two concurrent poster/filmstrip requests for the same local video collided on one temp filename (process id only, constant for the app's lifetime) and could corrupt or delete each other's output — each call now gets its own uniquifier, covered by a 4-thread concurrency test; a malformed OS-keychain entry hard-failed sync status and `disable(pool, true)` instead of reading as "no key," permanently wedging sync for that user — it now reads as no key, covered by a test; the "Show adult content" toggle was not honored by My List (the header badge and Settings → My List page), only by Home/Discover/Browse, contradicting the Adult-category feature's own documented behavior — fixed to match everywhere else; and rapidly toggling two genre chips in the manual category-override picker before the first save's request resolved could let a stale rejection's rollback undo the second, already-applied change — fixed with a latest-call-wins guard. `formatSize`'s unit suffixes and `formatDelay`'s "s" were also moved into the i18n catalog (see "Interface language" above).
- **Adding many links could look permanently stuck with no way to tell it apart from a hang.** `bulk_add_cmd` added each selected link's playlist strictly one at a time with no progress reported to the page — unlike testing links, which already streams a result per link as it lands — so the dialog showed one static "Adding…" for however long the whole batch took, with no way to distinguish "still working through a long list" from "actually hung." A handful of slow-but-reachable links in a large selection (each bounded only by the 30s HTTP fetch timeout, run one after another) could keep a user staring at an unchanged dialog for a long time. The add path now runs a few links at a time (`lumen_core::bulk::add_links`, the same bounded-concurrency/cancel shape `check_links` already used for testing, with its own 35s per-link timeout) and reports each result live as a `bulk://add-result` event, so the dialog shows "Adding… N of M" and updates as each link finishes; the existing Stop button now also cancels an in-progress add. Reproduced live against real IPTV aggregator playlists (iptv-org, up to ~11,300 channels in one list) before and after the fix; covered by Rust tests for concurrency, the already-known skip, and cancellation before anything starts.
- **A full runtime audit (0.1.7).** Every Tauri command (92 across `commands.rs`, `bulk.rs`, `cast.rs`, `privacy.rs`, `sync.rs`, `updater.rs`, `launch.rs`) was enumerated, then exercised: playback (play, pause, seek, volume, stop, Back-while-playing leaving a persistent mini-player), library browsing, the search engine (library + dedup), and Settings were driven live in the real app under Xvfb; two focused static passes covered the less-exercised modules (cast/privacy/updater/sync/launch, and TMDB/local-file/profile/search/episodes). Live testing found no crash or hang in any path it reached — playback against real but geo-restricted/unreachable IPTV streams failed the way the existing load-timeout already handles, not by hanging the UI. The static passes found four real concurrency bugs, now fixed: switching cast targets (`cast_start_cmd`) stopped the working session before confirming the new device actually started, so casting to an unreachable device threw away a perfectly good cast for nothing — the new session now has to succeed first; no `PRAGMA busy_timeout` was set on the SQLite pool, and the existing `foreign_keys` pragma was applied via a one-off query that (being per-connection) only ever reached one of the five pooled connections — both now run through `after_connect` so every connection gets them, and a write landing on another connection mid-transaction waits instead of failing at once with "database is locked"; the yt-dlp extractor update and the AppImage self-updater's install step had no guard against two concurrent calls (a double-click, or a manual action racing the background check) downloading to the same temp filename and interleaving writes — both now refuse a second concurrent call, and the extractor's temp file also gets a per-call uniquifier as defense in depth, the same fix already applied to thumbnail/filmstrip generation in the prior audit pass. Covered by new tests (cast's fix is a 3-line reordering with no new test scaffolding; the SQLite pragma is exercised by the existing full suite; the updater and extractor guards each have a dedicated concurrency test).
- **A full UI audit (0.1.7).** A screenshot-driven pass through the live app under Xvfb at its native 1440x900 window size, looking for anything that reads as unfinished rather than premium. Two concrete bugs turned up and were fixed first: the persistent "Now playing" dock is fixed-position on every page once something is playing, but no page reserved space for it, so the bottom ~90px of content (the last items in a long shelf, the Settings page's sticky Save bar) sat hidden underneath it — the app root now gets a `has-dock` class with padding sized to the dock's actual footprint; and a failed stream showed mpv's own short diagnostic bare and lowercase in a red strip ("something happened") with no framing, reading like a dev leftover — it now reads "Couldn't play this: \<reason\>". A punch-list of six smaller polish items was then worked through in priority order: the Discovery page was nearly empty (one shelf, ~450px of dead space) whenever no TMDB key is configured, since every other shelf depends on TMDB matching — it now also shows up to three "sample from your library" shelves (movies/series/live), split from the already-fetched recommendation list with no new IPC calls; card bottoms repeated the title that the artwork overlay already shows, so the heading is now screen-reader-only (`sr-only`) rather than removed, keeping per-card heading navigation; the player's idle/buffering state was flat black — it now shows the channel's own artwork, heavily blurred and dimmed, as a backdrop; the player's transport bar (subtitle/quality/speed/cast controls) was a row of bare `<select>`s and text buttons with no visual grouping — icons were added in front of each control, the subtitle tools and Cast button were grouped into pill-shaped clusters, and dividers now separate the clusters, while every control stays a native, fully keyboard-operable `<select>`/`<button>` (no new popover/listbox component); the active-filter chip's background and border reused the shared `--accent-soft` token at full strength, which read as a harsh red outline in the default theme — it now derives its own softer, theme-aware tint via `color-mix()` without touching the shared token; and the footer gained the installed app version and a GitHub link (`@tauri-apps/plugin-opener`, already wired for `AboutLumen.tsx`) in place of being just a tagline and a Settings link. All changes are CSS/TSX only, verified by screenshot at each step; no new i18n-gate violations (4 keys retired, 10 added).
- **A full-project audit pass.** A parallel read-through of every layer — `lumen-core` (two passes; came back clean, nothing new survived verification), the Tauri glue layer, the frontend, and the Cloudflare Worker sync server — found and fixed six concrete bugs. "Many links" could permanently wedge: `bulk_add_cmd` took its run lock before two fallible calls (`ensure_db`, `list_playlists`) that could return early with `?`, skipping the lock's own cleanup line and leaving every later check/add refused with "already running" until restart — an RAII guard now clears the lock on every exit path, not just the happy one (`bulk.rs`). A Stop clicked while the player's automatic fallback-to-next-source lookup was still in flight could be silently undone: the fallback's `.then` applied unconditionally once it resolved, resuming playback of an unrelated source after the user had already stopped — a per-attempt epoch, bumped by Stop and by starting anything new, now lets a superseded fallback detect it and do nothing (`usePlayer.ts`). The sync server's per-group row cap counted every pushed item as a new row, even though the write is an upsert — an actively re-synced, near-full group (mostly re-pushes of items it already held) could be rejected well below its real row count; it now subtracts the ids already held before comparing to the cap, chunked to stay under D1's bind-parameter limit (`worker.ts`, covered by a new cap test; the chunking value was found by the first fix attempt hitting D1's real "too many SQL variables" error in the local dev test run). Changing the poster-frame-time setting called `std::fs::remove_dir_all` on the shared thumbnails directory directly, with no coordination against the semaphore poster/filmstrip generation holds while writing — a concurrent generation call's temp-file rename could land on a just-deleted parent and fail with a spurious "could not extract a frame" error, and the whole directory wipe needlessly invalidated filmstrips too, whose cache key never depends on this setting; filmstrips now live in their own cache directory, and the clear now waits for every ffmpeg slot first (`commands.rs`, covered by a new concurrency test). Switching cast targets held the `ACTIVE` lock for the entire connection attempt to the new device, freezing the status poll and any pause/seek/stop on the device already casting for the full ~10s a slow/unreachable target can take — a separate lock now serializes concurrent start attempts against each other without blocking status/control calls on what is already playing (`cast.rs`).
- **One source failing to load could blank the entire library, permanently.** Reported by a user who bulk-added over 100 M3U links: afterward the app showed no content at all, including after a full restart. `useChannels.ts` loads every source's channels in batches of 4 via `Promise.all`; if even one source's `list_channels` call rejects for any reason (a transient lock, a malformed row, a slow aggregator list), the whole `Promise.all` rejects, the catch block sets an error, and — since this happens before `setAllChannels` is ever called on the very first load — every other source's channels are discarded too, surfaced as "Couldn't connect to your library" even though most sources loaded fine. Because the same source fails the same way on every load, this never recovers on its own, including after restarting the app. The batched load now uses `Promise.allSettled`: every source that loads successfully is kept and shown, and only the source(s) that failed are named in a dismissible notice instead of blanking everything.
- **An external report of four high-severity bugs, independently verified against the code and fixed.** `titles`/`title_sources` — the tables automatic source fallback and "new since your last visit" both read — were only ever filled by a one-time startup backfill that runs once against whatever already existed; importing a playlist never wrote to them, so on a fresh install both features silently found nothing, forever. Importing a playlist now upserts the same two tables for its own channels (`db.rs`, covered by a test importing the same channel from two providers and confirming the second is already a ranked fallback for the first right after import). Deleting the active profile fell back to the oldest remaining profile even if it had a PIN, and the frontend's "lock once per session" guard never re-evaluated after that fallback, so a profile with no PIN could be deleted to land, unlocked, in a PIN-protected profile's history and My List. The lock check now runs on every profile-list reload and compares the active profile id against the one this session has actually verified (via a PIN check or confirmed to need none), set explicitly by the two places that legitimately unlock one — `ProfileGate`'s own unlock and a deliberate switch in Settings — so any other way the active profile changes is re-evaluated (`App.tsx`, `ProfileGate.tsx`, `ProfileSettings.tsx`). Turning network privacy on or off mid-session left an already-running mpv on the old side of the proxy until it happened to restart on its own, since `--http-proxy` only takes effect at mpv's own startup — toggling it now stops playback immediately so the next play starts a fresh, correctly configured mpv, failing closed the same way the relay itself does (`privacy.rs`). Re-casting a different item to the device already playing could stop the cast it had just started: the ordering fix from the 0.1.7 runtime audit (start the new session before tearing down the old one, so an unreachable new device can't destroy a working cast) sends that teardown `Stop` to the old session's device regardless of whether it's the *same* device as the new one — it's now skipped when they match (`cast.rs`). A fifth report — the sync protocol's pull cursor advancing by the client-supplied `updated_at` it has already seen, so a device joining later and re-uploading its own older-timestamped data becomes permanently invisible to a device whose cursor has already passed that timestamp — was confirmed and is now fixed (see below).
- **The fifth report above: the sync pull cursor now pages by a server-assigned sequence, not the client's own timestamp.** `worker.ts` gained a `sync_seq` counter (one row per group) that `pushItems` bumps once per push that lands at least one write, independent of the pushed items' own `updated_at`; `sync_blobs` gained a matching `seq` column, added with a guarded `ALTER TABLE` plus a one-time backfill (rows from before the column existed get `seq = 1`, not the column's own default of `0`, so a from-scratch pull — `since_seq=0`, i.e. `seq > 0` — still sees them). `pullItems` now serves either cursor: a new `since_seq` query parameter pages by `(seq, item_id)`; its absence keeps the original `since`-based, `updated_at`-ordered path exactly as it was, so an old client that hasn't updated yet keeps working unchanged, bug included, until it does. The Rust client (`sync.rs`) always sends `since_seq` now — `PullCursor` carries `seq` instead of `since`, and the now-unneeded `PULL_OVERLAP_MS` clock-skew margin is gone, since a monotonic counter has no skew to buffer against. `CURSOR_SETTING`'s stored key changed (`sync_pull_cursor` → `sync_pull_cursor_seq`), which forces every existing install to resync from scratch exactly once: the old key is simply never read again, and the new one reads as unset everywhere, falling back to 0. `SealedItem` gained an optional `seq` field, outside the AEAD's authenticated data (which still only binds `id`/`updated_at`/`deleted`), so decryption is unaffected. Verified live against real D1 via `wrangler dev` — including that D1 does support `RETURNING` on `UPDATE`, which the seq-increment relies on — with a new end-to-end case in `sync-server/test/sync-flow.mjs` that reproduces the original bug (a late-joining device's old-timestamped push, invisible to a `since`-only cursor already past that timestamp) and confirms a `since_seq` cursor receives it; the in-process Rust mock (`sync_tests.rs`) mirrors the same seq bookkeeping, with a dedicated regression test reproducing the same scenario end-to-end through the real client code. **Deployed and verified live**: shipped via `wrangler deploy` against the production Worker and D1 database, then checked end-to-end against the live URL (real proof-of-work solved, a group created, an item pushed, a `since_seq` pull confirmed to return it with a `seq` field, test group deleted afterward) rather than just trusting the deploy command's own output.
- **The medium/low findings from the same external report, independently verified against the code.** Nine were real and are fixed; one is real but deferred (below), since fixing it properly touches the sync protocol and needed more care than this pass. The sync scheduler's debounce loop could silently drop a change made in the narrow window between it deciding to stop and actually clearing its "a cycle is running" flag — closed by having the loop re-check for a pending request immediately after clearing that flag and reclaim it if one landed there, instead of only checking once before (`sync.rs`, covered by a unit test of the extracted recheck step). The profile-PIN attempt limiter checked the lockout, then separately awaited the (comparatively slow) PIN verification, then recorded the result — a burst of concurrent guesses could all pass the check before any of them was recorded, trying far more PINs than the limiter intends; it now charges the attempt in the same lock acquisition as the check, before anything async runs (`pin_guard.rs`, covered by a 50-thread concurrency test proving a burst still costs exactly as much as a sequential run would). Restarting into a freshly-installed update slept a fixed 1 second before launching the new copy, guessing how long this process takes to shut down; too short a guess (plausible under load, with a slower WebView engine, or open connections) hands the new copy's single-instance check to the old process while it's still exiting, and neither one ends up running — it now polls this process's own pid and starts the new copy the instant it actually exits, capped at 10s so a stuck shutdown still gets a restart attempt (`updater.rs`). Toggling pause optimistically flipped the *current* paused flag after awaiting the pause command, but mpv's own `player://state` push can land during that await and already apply the real value — flipping it again afterward could land on the wrong state; the target is now decided before the await and set directly, so a race with the real push is a harmless no-op either way (`usePlayer.ts`). An IPv6 upstream proxy address (`socks5://[::1]:9050`) parsed with its brackets still attached (`[::1]`, not `::1`) and was then handed straight to `TcpStream::connect`, which does not understand bracket notation on a bare address and would try to resolve the literal text `"[::1]"` as a hostname — IPv6 proxies were unusable; `parse_upstream` now strips the brackets, covered by a new test (a dotless LAN hostname like `myproxy` was already fine). Remote images (TMDB art, `tvg-logo`) could load directly, unguarded, for however long it took the frontend's one startup call to read whether network privacy was actually on, since the local flag defaulted to "off" until that read resolved — even when the saved setting was on; it now defaults to "unknown" and is treated the same fail-closed way as "on" until the real value arrives, closing that startup window (`networkPrivacy.ts`; the fail-closed decision itself is pulled into its own Tauri-free module, `remoteImage.ts`, so it has a plain unit test instead of only ever running inside a mounted component). The yt-dlp extraction runner's output-cap check ran only inside the thread reading stdout, which just stops reading once the cap is hit — with nothing left draining the pipe, the child's next write blocks, and the process sat alive until the *unrelated, much longer* overall timeout finally noticed and killed it, rather than being killed as soon as the cap was actually hit; a shared flag now lets the main wait loop kill it immediately, covered by a test proving a process that floods output past the cap is killed in well under a fifth of a 20s timeout, not near it (`extract.rs`). SQLite ran in its default rollback-journal mode, where a writer blocks every reader for the length of its transaction - `busy_timeout` (added in an earlier pass) only ever papered over the resulting contention with a wait-and-retry, not real concurrency; the pool now also sets `journal_mode = WAL` and its standard pairing `synchronous = NORMAL` (`db.rs`). The sync Worker's `createGroup` checked for an existing group, then separately inserted a new row with no `ON CONFLICT` guard — two requests racing to create the same brand-new group (the same client's own retry arriving twice, in practice) could have the loser throw a raw UNIQUE-constraint error instead of the graceful "already registered" response a repeat registration is otherwise designed to give; the insert now ignores a conflict and settles on whatever ended up in the table, covered by an 8-way concurrent-create case in `sync-flow.mjs` (local `wrangler dev` serializes these enough that it did not actually force the race, but confirms no request ever sees a raw error either way). Three separate, independently-maintained lists of "which file extensions does Lumen treat as playable" had quietly drifted apart: the Local Device folder browser and the poster-generation gate both recognized fewer video/audio types than `launch.rs`'s "Open with Lumen" classifier (missing `m4v`, `mpg`, `mpeg`, `ogv`, and `aac` for the folder browser) — a file the OS would happily open with Lumen could be invisible when just browsing its folder in the app. Both now reuse `launch.rs`'s lists directly instead of keeping their own copies, covered by a test that iterates the canonical lists and asserts the other two agree with every entry.
- **Deferred from the same pass: a favorite or history row's `content_key` can go stale relative to a channel's current, better-matched identity.** `content_key::derive()` prefers a TMDB match over a `tvg:` id over a content-free hash of the stream URL, but the one-time backfill that assigns a `content_key` to an existing row only ever touches rows `WHERE content_key IS NULL` (`db.rs`) — once a row has *any* key, even the weakest hash-of-URL fallback assigned before TMDB ever matched the title, it is never revisited even after a later re-import computes a stronger key for the same channel. The most visible symptom (does a channel still show as favorited) is already covered by `is_favorite`'s existing `OR channel_url` fallback, so this was not reproduced as a user-visible "lost favorite." The real exposure is narrower but still real: a stale key stops participating in anything that groups or matches purely by `content_key` going forward — automatic source fallback, category overrides, and the sync protocol's own dedup — for a favorite/history row from before its title was ever matched. Fixing this fully means re-keying affected rows *and* correctly migrating their already-synced records (tombstone the old key, push under the new one), which is sync-protocol-sensitive work in the same vein as the pull-cursor fix above; it was not rushed into this pass.
- **Search and discovery** classify movies, series and live TV from names and groups, not catalog metadata. All library rows are held in memory; shelves virtualize the DOM but very large libraries need pagination.
- **Manual category correction.** A title TMDB never matched can have its Kind and Genre(s) corrected by hand from its details (`category_overrides`, keyed by `content_key` so the correction survives re-imports). Refused once TMDB actually matches the title, which stays authoritative; covered by Rust tests (merge into `list_channels`, rejection on a TMDB match, one correction shared by two rows with the same `tvg-id`, clearing reverts to the inferred guess) and TS tests for the override's priority against `tmdb_type` and the inferred fallback.
- **Adult content classification.** A regex over `group_title`/name keywords (`xxx`, `porn`, `adult`, `18+`, `nsfw`, `erotic`) flags adult titles; they are hidden everywhere (Home, Discover, My List) unless the off-by-default "Show adult content" toggle in Settings → Appearance is turned on and saved. The classifier is a heuristic over free-text playlist data, like the existing genre/kind guesses, so it can both miss unlabeled adult content and false-positive on an unrelated title that happens to share a keyword.
- **Online subtitles depend on unofficial services.** The Stremio mirror and Gestdown are not offered to third-party apps, can change or block without notice, and cover different things (Gestdown is TV only). Matching a title to an IMDb id by name is fuzzy. Podnapisi and OpenSubtitles.com were not added (Podnapisi could not be reached from the test machine; OpenSubtitles.com needs each user's own key). yt-dlp's subtitle fields were tested on recorded JSON, not against the pinned binary on a real site. While the Find dialog is open over single-window playback, the video can sit above it (untested on a real window manager).
- **Interface language.** Every screen reads its text from the catalog and a test enforces it, but only English exists. The gate scans `.tsx` files for JSX text/attributes; a plain `.ts` helper that builds user-visible text outside JSX (there were two — `formatSize`'s "B"/"KB"/"MB"/"GB" and `formatDelay`'s "s", now migrated to the catalog) is outside its reach and has to be caught by hand. Backend error text, genre/category labels derived from English playlist group names, and the strings of your own playlists stay as they are. The rendered text of 21 screens was compared before and after the migration (identical except one fixed plural and the new notification setting).
- **Network privacy has not been checked against a real proxy with real traffic.** The relay, mpv/yt-dlp wiring and image fetching are covered by unit and fake-upstream tests, and the app builds and runs with the feature compiled in, but no one has pointed it at a real SOCKS5 or HTTP proxy (a real VPN client, Tor, Shadowsocks) and watched the actual network with `tcpdump`/Wireshark to confirm nothing leaks. The WebKitGTK proxy hook compiles against the real crate and is unit-tested at the pure-function level, but has not been checked against a running webview on a real desktop. "Test connection" always uses whatever is currently typed into the password field, never a previously saved one (the backend command has no way to read it back from the keychain for this). The remote-image cache is a simple size-capped map, not a real LRU, and is unbounded by nothing but that cap for the life of the window.
- Extra mpv arguments are a trusted-local feature: whitespace-split, no shell involved.
